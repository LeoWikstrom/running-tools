# Running audio guide – build plan for Claude Code

Oct 20, 2026 · @Leo

## Goal and feasibility

Build an audio guide for running: the user prepares a course (an uploaded GPX, or one generated by the app), the app finds interesting places along it, writes a short summary of each, turns it into audio and, during the run, plays it when the GPS detects the runner has reached the place. It is buildable with open data (Wikipedia, Wikidata, OpenStreetMap) and with the text-to-speech engine already present in Android.

The app has two halves with different requirements:

- **Preparation** (before the run): map, course, place search, texts, audio. Must work on the web (desktop and phone) and inside the Android app. It is one web code base, loaded in the app inside a WebView.
- **Playback** (during the run): GPS with the screen off and audio with the phone in a pocket. Only the native Android app can do this reliably; on the web it exists as a screen-on preview.

The exchange format between the two halves is a `tour.json` file (course, places, texts, audio references), imported into the app the way Sylvester imports `plan.json`: open-with, share-to or an Import button.

Definitions:

- **Place**: a point with name, coordinates, source, interest score, summary text and audio file.
- **Trigger point**: the point on the course closest to the place, with its distance along the course in metres; the audio starts when the runner reaches it.
- **Tour**: course + places ordered by distance along the course + settings (language, target audio length, minimum spacing between places).

Decisions already taken (23 Oct 2026): narration language defaults to English; audio length defaults to 30–45 s and is user-selectable; texts come from Wikipedia only in v1 (LLM rewriting is a later phase); Gothenburg is the test city.

Scope of version 1: uploaded GPX, places from Wikipedia and OSM, summaries from Wikipedia, audio from Android text-to-speech, playback during the run. Out of scope: accounts, sharing tours between users, turn-by-turn voice navigation.

## Architecture and reuse

Decision: one monorepo with a shared TypeScript package (`core`), two web front-ends (`profile-course` and `runtour`, both Vite) and an Android app in plain Java without Gradle, built with the same `build.sh` approach as Sylvester (aapt2, javac, d8, apksigner). The Android app ships the `runtour` web build as an asset and shows it in a WebView, so preparation is identical on the web and in the app with no duplicated code. Only the player and the bridge to the system are native.

Layout:

```markdown
running-tools/
  packages/core/        shared: gpx, geo, graph, net (overpass, terrain, cache), search (beam, dijkstra, ksp), export
  apps/profile-course/  the elevation-profile course app (existing plan), now importing from core
  apps/runtour/         audio-guide preparation: map, places, texts, preview, tour.json
  android/runtour/      plain Java: WebView + JS bridge, GPS foreground service, audio player, TTS, tour import
```

What is reused from the elevation-profile app, moved into `core` in phase 0:

| Module | Reuse in the audio guide |
| --- | --- |
| `gpx/parse`, `gpx/export` | Reading the uploaded GPX; exporting the generated course and the places as waypoints |
| `shared/geo` (haversine, projection) | Distance from places to the course, distance along the course, closest point on a polyline (new, small function) |
| `net/overpass`, `graph/build`, `net/cache` | Pedestrian graph for course generation; the same query plus the tags `historic`, `tourism`, `memorial`, `artwork` on ways and nodes |
| `search/beam`, `dijkstra`, `ksp`, `improve` | Course generation with a different score (section 6); the beam-search structure stays the same |
| `ui/map` (Leaflet), bottom sheet, error states | Same base UI, same mobile conventions |
| IndexedDB cache | Overpass responses, Wikipedia geosearch, summaries |

What is new:

1. `core/poi`: place search, corridor filter, scoring and selection (section 3).
2. `core/text`: fetching and trimming summaries (section 4).
3. `core/tour`: `tour.json` types and validation, trigger-point computation.
4. Native bridge (`window.RunTour`, via `addJavascriptInterface`): `fetchText(url)` without CORS limits, `synthesize(text, lang, file)` using Android TTS, `saveTour(json)`, `startRun(tourId)`, `getLocation()`. On the web the same functions exist with weaker alternatives (section 4) or are disabled with a clear notice.
5. Native player (section 5).

Network inside the WebView: page `fetch` is subject to CORS exactly as in a browser (Wikipedia, Wikidata and Overpass allow it); official websites go through the native bridge. Maps inside the WebView: OSM tiles over the network, as on the web; prepared tours work offline because the player does not use the map.

## Finding the places

Places come from three sources, merged and deduplicated, filtered to a narrow corridor around the course, then ranked by interest and thinned out so that audio clips do not overlap.

| Source | Call | What it gives |
| --- | --- | --- |
| [Wikipedia geosearch](https://www.mediawiki.org/wiki/API:Geosearch) | \`action=query&list=geosearch&gscoord=lat | lon&gsradius=10000&gslimit=500\` on the local-language Wikipedia and on English Wikipedia |
| [Wikidata SPARQL](https://query.wikidata.org/) | Items with coordinates (P625) inside the course's bounding box, with P1435 (heritage designation), P31 (type), P856 (official website), P18 (image), sitelink count | Notability and type even without a page in the right language; link to the official site |
| OSM (already downloaded for the graph) | Nodes and ways with `historic=*`, \`tourism=attraction | museum |

Pipeline (`core/poi`):

1. **Bounding box and corridor**: fetch the sources for the course's bounding box padded by 300 m; for long courses (over 10 km) split into 5 km boxes and merge. Keep only places within 80 m of the polyline (`corridorWidth`, adjustable up to 150 m for squares and parks).
2. **Deduplicate**: merge by Wikidata id when present, otherwise by normalised name within 50 m.
3. **Interest score** (0–100): Wikidata sitelinks (weight 0.4), Wikipedia page length (0.2), heritage designation present (0.2), type in a list of "worth telling" types (church, castle, museum, monument, historic bridge, square, theatre, stadium) (0.2). OSM-only places with no name or none of these signals are dropped.
4. **Trigger point**: project the place onto the polyline → distance along the course `d`. If the course passes the same place twice, keep the first pass.
5. **Thinning**: sort by `d`; when two places are closer than `minSpacing` (default 200 m, about 50–60 s at easy pace, which fits the 30–45 s clips) keep the higher score. Default cap of 25 places per tour; the user can remove or add places by hand on the map and search for more by name.
6. **Lead**: the audio should start just before the place, not on top of it. The effective trigger point is `d − leadDistance`, where `leadDistance` = 10 s × expected pace (default 5:30/km → about 30 m).

Language: the geosearch runs on the local Wikipedia (country from Wikidata P17) and on English Wikipedia; the final text is in the narration language, English by default (section 4).

## Texts and audio

Each place gets a text of 30–45 s spoken (about 70–110 words) by default, adjustable per tour from 20 to 120 s, in the narration language (English by default), generated before the run, plus an audio file stored locally. Nothing is downloaded or synthesised during the run.

**Text sources** for v1, in order of preference:

1. [Wikipedia REST summary](https://en.wikipedia.org/api/rest_v1/) `/page/summary/{title}` on English Wikipedia, then on the local-language Wikipedia: gives the lead extract, already short and neutral. Licence CC BY-SA: the tour shows "Source: Wikipedia" and the link.
2. "History" or "Architecture" sections of the full page (`action=parse&prop=sections`, then `section=N`) when the extract is under 40 words.

**Trimming** (v1, no LLM): cut the extract at the sentence boundary closest to the target length, drop parenthesised pronunciations, coordinates and reference markers, and prefix one spoken line: "You are passing \<name>." If the only available page is in another language, show the original text, mark the place as needing review, and let the user write or paste a text by hand.

**LLM rewriting** (phase 7, optional): a model rewrites the material in the narration language as a short guide's narration, second person, with the target length, no date lists, one curious fact if there is one. The API key is the user's own, stored locally. The prompt is constrained to the material provided; the source is always shown.

**Text-to-speech**, by platform:

| Where | Engine | Notes |
| --- | --- | --- |
| Android app | `TextToSpeech.synthesizeToFile` (system Google TTS voices, also offline) | Free, good quality in English, Swedish and Italian; one WAV or MP3 file per place in `files/tours/<id>/` |
| Web, preview | Web Speech API (`speechSynthesis`) | Live, not saveable, variable quality; only for checking the texts |
| Web, full tour (optional, phase 7) | Cloud TTS (Google, Azure, OpenAI) with the user's key, via a small proxy | Produces the audio files without the app; only if needed |

`tour.json` carries the texts and the audio file names; if a file is missing, the player synthesises on the fly with the system TTS as a fallback, with about one second of delay.

`tour.json` format (versioned, `version: 1`): `{ id, name, lang, createdAt, route: { points: [[lat, lon, ele?]], distance }, settings: { corridorWidth, minSpacing, leadDistance, paceSecPerKm, targetSeconds }, places: [{ id, name, lat, lon, d, triggerD, score, sources: [{kind, url}], text, audio?: filename }] }`.

## The player during the run

The player is an Android foreground service (`RunService`) with a persistent notification. It reads the GPS once a second and plays a place's audio when the runner reaches it; it works with the screen off and the phone in a pocket, and keeps running if the WebView is closed.

**Location**: `LocationManager.GPS_PROVIDER` first, since it needs no dependency and the Gradle-free build has no Play Services libraries; consider `FusedLocationProviderClient` only if accuracy turns out insufficient. Interval 1 s. Permissions: `ACCESS_FINE_LOCATION`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_LOCATION`, `POST_NOTIFICATIONS`. Ask the user to exclude the app from battery optimisation, with a one-line explanation.

**Trigger logic** (`core/tour/runtime.ts`, re-implemented in Java with the same algorithm; the unit tests live in TypeScript and their cases are exported as JSON and replayed in Java):

1. Project the position onto the course polyline → distance along the course `dNow` and lateral offset `off`.
2. If `off` > 60 m for more than 20 s: state "off course", no triggers, one short beep.
3. A place triggers when `dNow ≥ triggerD` and `dNow < triggerD + 150 m` and it has not been played yet. The upper bound avoids playing skipped places when the runner cuts the course; the user can replay them from the notification.
4. Queue: if a clip is playing, the next one waits; if it has waited more than 200 m past its point it is dropped (better to lose one than to narrate it in the wrong place).
5. Loops run more than once: `dNow` always follows the nearest point forward of the last one, never more than 100 m backwards.

**Audio**: `MediaPlayer` with speech-type `AudioAttributes` and an audio-focus request of `AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK`, so music ducks during the narration and comes back afterwards. Works with Bluetooth headphones and the speaker. A short chime (0.3 s) precedes each clip.

**Run screen** (native, not WebView, to stay light): next place and distance to it, buttons Pause, Skip, Repeat, Finish; the same controls in the notification and, optionally, on headphone buttons (`MediaSession`). At the end: list of places narrated, skipped and missed, with links to the sources.

**Web preview**: the same `runtime.ts` driven by a simulated position moving along the course at the set pace, texts read by the Web Speech API; used to check order, lead and clip length without leaving home. On the web with the screen on, real GPS (`watchPosition`) also works, with a notice that it stops when the screen turns off.

**Battery**: with 1 s GPS and occasional audio, expect roughly 8–12 % per hour, similar to a tracking app; acceptable for runs of up to a couple of hours.

## Course generation

The "N km course that passes the most interesting places" uses the same beam search as the elevation-profile app, changing only the score function and two constraints. It is the advanced phase and comes after everything else works with an uploaded GPX.

Differences from the elevation-profile app:

1. **Places first, then the course**: fetch the places within the radius (section 3, without the corridor filter) and snap each place with score ≥ 30 to the nearest graph node within 60 m. An edge touching that node "collects" the place.
2. **Score** (higher is better, the opposite of the other app; flip the sign to reuse the code):

```latex
S = \sum_{\text{collected places}} \mathrm{interest}_i \;-\; w_r \cdot \mathrm{repeats} \;-\; w_p \cdot \mathrm{penalties} \;-\; w_d \cdot |L - L_{\text{target}}| \;-\; w_s \cdot \mathrm{crowding}
```

- `interest` is the score from section 3; a place counts once.
- `crowding` penalises places closer than `minSpacing` along the course, so the optimiser does not pile ten churches into 400 m.
- `penalties` reuse the safety weights of the other app (roads without sidewalks, steps), plus a light bonus for `highway=pedestrian` and parks: in a tourist city, pedestrian zones run better.

3. **Constraints**: return to start on by default (a visitor leaves from and returns to the hotel); length tolerance ±5 %.
4. **Beam**: states remain `(node, distance bucket)`, but the partial score is not decomposable per edge once a place has been collected; the state carries a bitset of collected places (at most 64 candidate places per search, the best by score). Two states on the same node and bucket with different bitsets both survive.
5. **Local improvement**: identical (300–1 500 m windows with k-shortest-paths), with the new score.

UI: start point, length, an implicit radius of `length / 2 × 0.6`, and three sliders: "more places / more direct", "pedestrian only / roads too", "historic centre / outskirts too" (the last weights distance from the centroid of the places). The result can be adjusted by dragging the course onto a different edge, then the normal pipeline follows (corridor, texts, audio).

## Implementation phases

Seven phases; each ends in something usable. Claude Code finishes one phase, runs its tests, commits, and only then starts the next. From phase 4 onward you can actually run with the audio guide.

**Phase 0 – Monorepo and shared core** (1 day)

- [ ] Create `running-tools/` as an npm workspace; bring the existing repo \~/personal\_projects/profile-course in as apps/profile-course (git subtree or a plain move, keeping its history if easy), then move its modules listed in Architecture into `packages/core`; `apps/profile-course` imports from `core` and its tests still pass.
- [ ] Add point-to-polyline projection (distance along, offset) to `core/geo`, with tests.
- [ ] Skeleton of `apps/runtour` (Vite, Leaflet, bottom sheet) that loads a GPX and shows it.

* Done when: both apps start from `npm run dev` in Termux and the `core` tests pass.

**Phase 1 – Places** (2 days)

- [ ] Wikipedia geosearch and Wikidata SPARQL clients with cache; place extraction from the OSM data.
- [ ] `core/poi` pipeline: corridor, dedupe, score, trigger point, thinning. Tests with a fixed course and saved responses.
- [ ] Map: places as markers with score, toggleable; search by name.

* Done when: for a GPX around central Gothenburg the course shows a sensible list of 10–25 places ordered by distance.

**Phase 2 – Texts** (1 day)

- [ ] Wikipedia summaries (summary endpoint, then sections); trimming to the target length with the rules in Texts and audio; target length selector (default 30–45 s).
- [ ] Text editor in the bottom sheet (edit, refetch, delete, mark as reviewed).
- [ ] Export of `tour.json` and of the GPX with waypoints.

* Done when: a complete tour saves and reopens; the texts read well aloud in English.

**Phase 3 – Android app, shell** (2 days)

- [ ] `android/runtour` project modelled on Sylvester: `build.sh`, manifest, an activity with a WebView loading the `apps/runtour` build from assets; `tour.json` import via open-with and share-to.
- [ ] `window.RunTour` bridge: `fetchText`, `synthesize` (system TTS to file), `saveTour`, `listTours`.
- [ ] Audio generation for a whole tour with a progress bar; files in `files/tours/<id>/`.

* Done when: a tour prepared on the phone has all its audio and can be listened to from the tour list.

**Phase 4 – Run player** (2–3 days)

- [ ] `runtime.ts` with tests; the same logic in Java replaying the exported cases.
- [ ] `RunService` with GPS, triggering, audio queue, audio focus, notification with controls.
- [ ] Native run screen and end-of-run summary.
- [ ] Field test on a familiar loop in Gothenburg with 5 places; tune `leadDistance` and the trigger window.

* Done when: a 5 km run with the screen off plays every place at the right spot.

**Phase 5 – Web preview and polish** (1 day)

- [ ] Preview with simulated position and Web Speech API in `apps/runtour`.
- [ ] Error states, offline, languages; static deploy of the web app.

* Done when: a tour can be prepared on a computer, sent to the phone and run.

**Phase 6 – Course generation** (3 days)

- [ ] Snapping places to nodes; bitset score; beam search and local improvement reused from `core/search`.
- [ ] UI with the three sliders; manual adjustment of the course.

* Done when: from a start point and 8 km the app proposes a loop touching at least 8 places with score ≥ 30 and avoiding roads without sidewalks.

**Phase 7 – Later** (optional): LLM rewriting of the texts with the user's API key; official websites via the native bridge and a proxy; cloud TTS from the web; place photo in the notification; export of places as proximity-alert waypoints for a Garmin watch.

## Risks and decisions

| Risk | Likelihood | Mitigation |
| --- | --- | --- |
| City GPS (urban canyons) is off by 20–40 m and triggers audio too early or late | High | Use distance along the course, not distance to the place; wide trigger window; adjustable `leadDistance`; filter on position jumps |
| Android kills the service with the screen off (some manufacturers especially) | Medium | Foreground service with notification, battery-optimisation exemption requested on first run, partial `WakeLock` during the run |
| Wikipedia has little or nothing on minor places, or only in the local language | High outside big cities | Multiple sources, manual text editing, "needs review" flag; LLM translation in phase 7 |
| Trimmed extracts start mid-thought or keep irrelevant detail | Medium | Sentence-boundary cutting, cleanup rules, mandatory review in the preview before running |
| Gradle-free Android build: no Play Services, so no `FusedLocationProviderClient` | Medium | Start with `LocationManager` (no dependency); revisit only if accuracy is insufficient |
| System TTS voice missing for the chosen language | Low | Detect installed languages and show how to download the voice; fall back to the phone's language |
| Monorepo quality: the refactor into `core` breaks the elevation-profile app | Low | That app's tests remain the phase 0 criterion |

Decisions taken on 23 Oct 2026:

- Narration language defaults to English.
- Clip length defaults to 30–45 s; the user can change it per tour.
- Version 1 uses Wikipedia only; LLM rewriting is phase 7.
- Gothenburg is the test city for phases 1–6.
